# simstim Stage 0.9 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Two owner-requested settings: re-transcribe automatically when a recording stops, and delete the call audio once a re-transcribe succeeds.

**Architecture:** Config gains two booleans. `stop_recording` enqueues an auto job when enabled; the re-transcribe module grows a small FIFO queue so a second stop cannot be rejected by the single-job guard. A successful re-transcribe deletes the session's audio when the second setting is on. The settings dialog gets both toggles, gated on `keep_audio`.

**Tech Stack:** existing workspace, no new dependencies.

## Global Constraints

- Config gains `auto_retranscribe: bool` (serde default **false**) and `delete_audio_after_retranscribe: bool` (serde default **false**). Old config.json files load unchanged and behave exactly as today. Commands: `set_auto_retranscribe(bool)`, `set_delete_audio_after_retranscribe(bool)`.
- **Delete-after applies to EVERY successful re-transcribe**, manual or automatic. A setting whose meaning depends on how the action was triggered is confusing; the UI copy states the consequence plainly instead.
- Delete-after fires **only on success** (the transcript was actually rewritten). Any failure path, including the existing "whisper found no speech" abort, leaves the audio untouched.
- Deleting the audio removes exactly the session's own audio sibling(s) resolved by the existing `resolve_audio_path` chain (`.flac` / `.m4a` / `.wav` / `.recording.wav`), never anything else. Failure to delete is reported via the existing error surface, not silent.
- Auto-retranscribe triggers when a recording stops normally (`stop_recording` succeeded and produced a session path) AND `auto_retranscribe` is on AND `keep_audio` is on. It never triggers for a session with no audio.
- **Queue, not rejection.** Re-transcribe currently allows one job at a time. Add a FIFO queue of pending session paths in the re-transcribe state: when a job finishes (success or failure), the next queued path starts automatically. Manual invocations queue the same way rather than being rejected with "another job is running". Guard against queueing the same path twice, and never queue the actively recording session.
- Auto jobs must not spam errors: when the selected whisper model is not downloaded, report once through the existing `retranscribe-progress` error phase (the UI already surfaces it) and drop the job rather than retrying.
- UI: both toggles live in the Output section under the existing "Keep call audio" checkbox. When `keep_audio` is off, both are disabled with a muted explanation ("Needs call audio"). The delete toggle's helper text must state the consequence: the recording is removed and the call cannot be re-transcribed again. Same error-handling pattern as the other settings rows (optimistic set, revert on failure, inline error).
- Existing behavior preserved: single-writer rule, atomic writes, the finalizing-window rejection, no telemetry, light and dark both fine.
- Conventional commits, no AI co-author lines, no em dashes in authored copy. Every task ends with `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, `pnpm test`, `pnpm build` green.

### Task 1: Config, queue, auto trigger, delete-after

**Files:** `apps/desktop/src-tauri/src/config.rs`, `retranscribe.rs`, `lib.rs`, `apps/desktop/src/lib/ipc.ts` (types and wrappers only, no UI).

**Interfaces produced:**
- `Config::auto_retranscribe`, `Config::delete_audio_after_retranscribe` + their two commands.
- Re-transcribe state gains a pending queue; the existing "another job is running" rejection is replaced by enqueueing. Keep every other rejection (actively recording, finalizing, missing audio, missing model, retired model) exactly as is.
- `stop_recording` enqueues the just-stopped session when the settings allow it. Stop must NOT block on the job: it returns as soon as the recording is finalized, exactly like today.
- On a successful re-transcribe, when the setting is on, the audio file is deleted and the "done" progress event still fires afterwards.

Tests: config defaults + old-config load; queue drains in FIFO order and a second stop does not get rejected; the same path is not queued twice; a failed job still drains the queue; delete-after removes the resolved audio only on success and leaves it on every failure path (including the empty-whisper-result abort); delete-after off leaves audio alone; auto trigger does not fire when `keep_audio` is off or when the model is missing (reports once instead).

## Self-review notes

- The queue is the load-bearing piece: without it, "auto re-transcribe" plus any manual click produces a rejected job and a confusing error, and the owner would hit it the first time he stops a call while an earlier one is still running.
- Delete-after is destructive and irreversible by design (the owner asked for it); the guard rails are success-only, resolved-path-only, and explicit copy.
- Interaction with `keep_audio` is the one place where three settings meet: the UI disables rather than silently no-ops, and the backend re-checks anyway.
